# Architecture

Ushot is a native, local-first macOS application with bundle identifier `io.github.ischeneycc.ushot`. The shipping `UshotApp` target is an AppKit/SwiftUI hybrid and the reusable implementation lives in `UshotCore`. `Package.swift` compiles the same sources used by the Xcode project, so command-line validation cannot drift into a second implementation.

## Boundaries

- `UshotApp`: process lifecycle, SwiftUI settings scenes, menu-bar presentation, AppKit windows and dependency assembly.
- `UshotCore/Capture`: public ScreenCaptureKit adapters, capture requests/results, state coordination and test doubles.
- `UshotCore/Geometry`: the only coordinate conversion layer between AppKit global points, ScreenCaptureKit frames and image pixels.
- `UshotCore/Annotation`: versioned document, tools, commands, undo and hit testing.
- `UshotCore/ImagePipeline`: Core Graphics/Core Image rendering and caching.
- `UshotCore/Export`: color-managed PNG/JPEG/TIFF Image I/O encoding, clipboard representations and filename generation.
- `UshotCore/History`: versioned atomic on-disk records. Disabled by default.
- `UshotCore/Color` and `UshotCore/Measurement`: system-managed live pixel sampling and point/pixel ruler calculations.
- `UshotCore/Settings`: a versioned Codable settings schema and its persistence boundary.
- `UshotCore/Product`: the single source of truth for the public name, permanent bundle identifier, Application Support namespace and legacy identity migration keys.
- `UshotCore/FeatureGating`: the single future entitlement seam. Capture and drawing code never contains payment checks.
- `UshotCore/Logging`: privacy-safe OSLog categories. Pixel data and user content are never logged.
- The application update adapter: the only network-capable boundary. It wraps Sparkle for explicit manual checks and remains replaceable through `UpdateChecking`.

## Dependency Direction

The app target depends on `UshotCore`; the core never imports app UI. OS-facing implementations conform to protocols (`ScreenCapturing`, `PixelSampling`, `CapturePermissionChecking`, `GlobalHotKeyManaging`, `AnnotationRendering`, `ImageExporting`, `ScreenshotHistoryStoring`, `FeatureEntitlementChecking`, `UpdateChecking`). Tests replace those boundaries without requesting screen-recording permission.

## Update and release trust boundary

The menu-bar command **Check for Updates…** is the only normal update-network admission point. It appears after Settings and before About Ushot and delegates to `UpdateChecking`; duplicate checks are rejected by Sparkle's `canCheckForUpdates` state instead of creating a second transaction. Automatic checks, automatic downloads and Sparkle system-profile submission are explicitly disabled.

The published 0.1.1 client is permanently isolated on `https://ischeneycc.github.io/ushot/updates/appcast.xml`; that legacy endpoint stays HTTP 404 and is never part of a Pages artifact. Ushot 0.1.2 (build 3) is the published first manual-install transition whose updater delegate always returns `https://ischeneycc.github.io/ushot/updates/v1/appcast.xml`, so a UserDefaults or launch-argument `SUFeedURL` override cannot redirect the request. A newly identified pre-parse validation gap requires 0.1.3 (build 4) to ship as a second manual GitHub-only transition with `publish_update_feed=false`; it is not yet published. The v1 endpoint remains absent until the separately reviewed first feed and online update, 0.1.4 (build 5). Published 0.1.1/0.1.2 artifacts retain their historical Ed25519 public key; the owner-approved pre-0.1.3 rotation changes the trust root only for the manually installed 0.1.3 and later chain, using Keychain account `io.github.ischeneycc.ushot.20260806` and public key `+zRL11/2yYePt5O+OetThnLGwyvAvFtPPXxiBBOTTjE=`.

`SURequireSignedFeed` authenticates the complete appcast, including its embedded Markdown descriptions, and signed-feed failure recovery is permanently disabled (`SUSignedFeedFailureExpirationInterval = 0`): a feed that cannot be verified never becomes usable with time. From 0.1.3 onward `SUMaximumSignedAppcastContentLength=1048576` limits the authenticated XML prefix to 1 MiB. Sparkle permits only a fixed 512-byte signature trailer above that prefix, rejects an oversized declared `Content-Length` before accepting the body, and enforces the same 1,049,088-byte wire ceiling incrementally for chunked or otherwise undeclared responses. This temporary-data bound is scoped to the appcast; the later persistent ZIP/archive download is not capped by it. The embedded framework advertises this transport contract with `SUFeedDownloadSizeLimitVersion=1`. That cryptographic signature alone does not make post-parse policy sufficient. Sparkle's `SUAppcastItem` construction can choose or flatten localized nodes, causing duplicate, misplaced or namespace-confused signed metadata to disappear from the host's view. The fork therefore calls the opt-in `updater:validateSignedAppcastData:error:` host hook (imported in Swift as throwing `updater(_:validateSignedAppcastData:)`) with the exact authenticated XML prefix after successful EdDSA verification and before XML parsing. The host sets `SURequireHostSignedAppcastValidation=true`, owns the hook for the complete updater lifetime and admits the framework only when `SUHostSignedAppcastValidationVersion=1`; rejection or loss of that owner produces `SUAppcastParseError` rather than falling back to ordinary item parsing.

The raw validator enforces the canonical RSS/channel/item hierarchy and namespaces, unique metadata and attributes, a single restricted-Markdown description and full enclosure, canonical version/archive identity, bounded UTF-8, and the absence of DTD/entity declarations. The existing parsed-item policy remains a second layer and accepts an update only when `signingValidationStatus == .succeeded`. Every item must have exactly one nonempty `description` with `sparkle:format="markdown"`; item-level `releaseNotesLink`, `link`, `fullReleaseNotesLink` and delta enclosures are rejected. `shouldDownloadReleaseNotes` always returns false, so Sparkle cannot fetch detached notes.

Embedded release descriptions use restricted Markdown. The release pipeline rejects links, images, raw HTML, autolinks, entities and URL/domain/network-address-like destinations in both the new source and every retained description, and applies the same raw structural invariants before signing or extending a feed. Accepted archives are immutable versioned ZIP assets from the official `https://github.com/isCheneycc/ushot/releases/download/...` boundary. The published 0.1.2 runtime embeds `https://github.com/isCheneycc/Sparkle` at exact immutable tag `2.9.5-ushot.2` and revision `f4d8362bf9b6231596db3a0cc8812fdca8100961`; its SwiftPM archive checksum is committed in the tagged fork manifest. That runtime requires `SURequireExactUpdateVersionIdentity=true`, `SURequireEdDSAUpdateArchiveSignature=true` and `SUUpdateVersionIdentityHardeningVersion=1`, but predates the authenticated-XML hook. Published tag `.3` is the historical authenticated-XML-hook predecessor and was not embedded in a published Ushot build. The 0.1.3 transition pins published successor tag [`2.9.5-ushot.4`](https://github.com/isCheneycc/Sparkle/releases/tag/2.9.5-ushot.4) at revision `3d81360ff115ffb80222c2723d72cb4cfa802774`; its SwiftPM ZIP SHA-256 is `d8d36e5b5ee9e97b17babc1beeb26795b96558cafe5450130aafa5b169d5c829`. It retains the existing gates and adds the host validation, bounded-feed key and framework markers above. After extraction and before installation, the fork compares both `CFBundleShortVersionString` and `CFBundleVersion` against the signed appcast item and requires the archive EdDSA result independently of matching application code signing. Missing or changed key configuration, host policy, hook ownership or framework marker disables the updater or rejects the feed with a privacy-safe fault; it must never start an unverifiable session or treat HTTPS/checksums/code signing as an archive-signature substitute. The fork release is verified dependency evidence, not a published Ushot 0.1.3 build or transition-matrix result.

Initial installation and in-app replacement are separate paths. The initial DMG contains `Ushot.app`; the user drags it to Applications and, because the public artifact has no Developer ID or notarization, removes only `com.apple.quarantine`. Sparkle consumes the ZIP enclosure for an update. The first public artifacts are intentionally ad-hoc signed with no Team ID or `get-task-allow`; public builds disable Hardened Runtime to avoid the unsupported ad-hoc/Library Validation combination blocking Sparkle helpers. Every mode embeds Sparkle and the executable carries `@executable_path/../Frameworks` in `LC_RPATH`; source/build/package/install checks fail closed if the framework cannot resolve. Local Apple Development signing is only a stable developer-install identity and is not the public trust mechanism.

The release transaction publishes `Ushot-<semver>-arm64.dmg`, `Ushot-<semver>-arm64.zip`, `Ushot-<semver>-arm64.dSYM.zip`, `Ushot-<semver>-arm64.release-manifest.json` and `SHA256SUMS.txt`. Runtime hardening does not fork the publishing format: the workflow uses the official upstream Sparkle 2.9.5 `generate_appcast --embed-release-notes` and verification tools, validates the same raw RSS/Sparkle structure, uniqueness and DTD/entity prohibition enforced at runtime, requires both the new semantic version and build to be strictly greater than every retained signed item, and signs the complete appcast. The committed `updates/v1/appcast.xml` seed is the sole zero-item migration input and may bootstrap only 0.1.4 (build 5); a pre-existing feed with detached, unrestricted or structurally ambiguous notes is rejected instead of being normalized or re-signed. The workflow separates read-only admission, credential-free release-artifact building, bounded opaque feed/tool preparation, a separate credential-free fixed-source signing-validator build, secret-free `release` approval, a job-level feed-only `update-feed-signing` runner, immutable signed-feed preservation, credential-free validation of a disposable copy, clean no-checkout Pages packaging, secret-free Release publication, read-only deployment admission and a pure pinned-action Pages deploy runner. Every cross-runner input is selected by immutable artifact ID and recovered with fail-on-digest-mismatch semantics. The builder compiles and ad-hoc signs both the app-identical authenticated-XML validator and canonical Ed25519 public-key deriver; the signer rebinds their exact two-file artifact by name, layout, independent binary SHA-256 values and strict code signatures, while the signed feed is bound by raw size/SHA-256 and Pages artifact REST identity. Existing feed bytes are authenticated and passed through the XML validator before any parser or Sparkle normalizer sees them, and private/public-key identity is checked only by the prebuilt deriver. Official Sparkle tools are checksum-pinned and freshly extracted; the signing runner invokes no source interpreter or compiler and only it briefly receives the EdDSA key through a non-logging channel. It repeats the prebuilt XML policy on the generated cryptographically verified feed and uploads those accepted bytes before any mutable repository validation executes. The later no-key validator reuses and rebinds the same immutable helper artifact instead of rebuilding the package. All versioned assets and checksums are uploaded and verified before the GitHub Release is published; the final runner has Pages/OIDC write authority but no checkout or shell, and deploys only the previously admitted artifact after the Release succeeds, so a client cannot discover a partial release.

The workflow also extracts the final ZIP and requires its `CFBundleShortVersionString` and `CFBundleVersion` to match the appcast. This publication check, pipeline raw-XML policy, host authenticated-XML hook and runtime fork's post-extraction check are independent defense-in-depth gates. Neither source review nor CI substitutes for the required runtime evidence: production deployment remains blocked until a clean-account 0.1.3 → 0.1.4 run proves raw-XML rejection, exact-version mismatch rejection and strict archive EdDSA behavior alongside the remaining transition matrix.

This trust design is not evidence of operational readiness. The 0.1.2 direct-download transition was published without a feed and must be installed manually. The 0.1.3 authenticated-XML transition must also be installed manually after it is published; it has not yet completed publication or release testing. Before 0.1.4 is deployed as the first `/updates/v1/appcast.xml` item, a clean-account 0.1.3 → 0.1.4 test must prove all three framework capability markers, the required host booleans and `SUMaximumSignedAppcastContentLength=1048576`, exact-production-URL declared/chunked size rejection, authenticated raw-XML rejection, Sparkle helper loading, archive/signature and short/build mismatch rejection, atomic replacement/relaunch, key recovery, quarantine behavior and Screen Recording authorization behavior. App actions, history operations, pinned-screenshot editing/output, capture sessions and Canvas editors participate in one update-admission boundary; new work is rejected while the updater owns a transaction, and Sparkle postpones relaunch until the same boundary reports no active work.

## State and Failure Model

Capture is serialized by a state machine: `idle → checkingPermission → preparingContent → selecting → capturing → presentingPinnedShot → quickEditing/canvasEditing → exporting → idle`. Admission atomically changes `idle` to `checkingPermission`; a second shortcut therefore cannot race between a separate state check and transition. When a session is active, the repeated request is rejected with a beep and privacy-safe lifecycle log before it owns any state. It cannot enter the active session's failure path, reset that session or present a modal alert behind capture-level panels. Cancellation and every error owned by an admitted request transition back to a stable state. Errors are surfaced to the caller and logged with context; they are not swallowed or silently replaced with fallback data.

Global shortcut recording classifies physical F1–F20 key codes separately from ordinary keys. A bare function key is admissible, while every ordinary global shortcut requires Command, Option, Control or Shift; Fn/Globe is an event-routing aid rather than a persisted modifier. One canonical admission predicate is enforced by the recorder, settings decode/persistence and the global registration boundary, so stale or malformed settings cannot bypass the ordinary-key guard. The same physical-key map supplies function-key labels, and the Carbon boundary receives the selected key code transactionally so a system reservation or conflict rolls back to the previous registration.

Region capture deliberately remains in `selecting` after mouse-up. Every display is frozen before the overlay appears, and that preparation remains the source of truth throughout confirmation. Cropping runs off the main actor only to maintain a hidden pixel/effect cache; confirmation itself continues to show the frozen overlay's selected pixels rather than a cropped screenshot preview. A transparent annotation surface at the selected desktop frame owns the single blue eight-handle chrome, while a prepared, recyclable toolbar owns annotation and output actions. Its lifecycle-aware composition hides Click Through, Temporarily Hide Image and Open Canvas Editor during confirmation, then restores those same arranged controls after Pin converts it into a pinned-image toolbar. At confirmation every full-screen frozen-overlay panel becomes visual-only (`ignoresMouseEvents = true`), so the annotation panel is the sole pointer-input owner instead of competing with a transparent screen-sized event sink. The chrome panel adds a transparent outer hit margin so every handle center can coincide with the true selection border without clipping; the four complete border lines are directional resize targets, not only their visible points. That margin is removed at Pin and never participates in capture geometry. The container explicitly frames the annotation canvas inside its panel instead of vertically constraining mixed coordinate systems, then routes border hits to the chrome and all interior hits to the canvas. This keeps the input surface exactly equal to the selected frame. Both panels disable AppKit window animations. The initial confirmation and every geometry update are canonicalized onto the same whole-point desktop grid before either the panel or canvas is changed, so live drawing and mouse-up commit never switch backing-pixel phase. Select-dragging empty canvas space uses a move transaction: it changes the desktop frame but preserves document-local annotation coordinates. A border resize uses a distinct global-anchor transaction: the container synchronously updates the canvas and chrome before display, while the canvas maps the preview selection back to the original global-desktop document as a 1:1 visible rect. An edge drag therefore only reveals or clips document space; it cannot move annotations or apply an axis-dependent transform to geometry, handles or strokes. Mouse-up refreshes the cache from the original frozen displays, then the editing session rebases its current document and every undo/redo snapshot to the committed selection.

Before manual selection begins, `RegionCapturePreparation` retains the ordered frozen ScreenCaptureKit window descriptors. Pointer hover resolves the first containing window immediately, so the visible snap frame and click acceptance do not depend on Accessibility. A short cancellable background refinement queries `AXUIElementCopyElementAtPosition` against that window's owning process, never against Ushot's overlay, and promotes a useful clipped child-control frame only when optional Accessibility permission is present. Dragging beyond the threshold leaves candidate mode and creates an ordinary manual rectangle. Permission absence is an explicit resolution and log state; it does not disable or fake window snapping.

Copy, Save and Pin are the three output-commit boundaries. Successful Copy or Save resolves the latest composite and destroys the overlay, annotation surface and toolbar; cancelling the Save panel does not commit. A window/display capture uses the same success-only dismissal for toolbar Copy and screenshot-level `Command-C`, while text-field copying remains native. Copy and Save acquire a generation-qualified output lease only after region recropping and pointer interaction have committed. That lease records the desktop frame, freezes canvas, resize chrome and toolbar mutation, and is validated after every asynchronous render boundary and immediately before writing. Escape, Cancel, replacement or termination cancels and invalidates the lease; a stale task cannot write output or invoke a lifecycle callback, and only the matching generation may restore input. Render/export failures are deduplicated at the owning action, release that lease first, then present one alert above the region surface and toolbar so the still-open screenshot can be retried. Pin resolves the same composite, destroys the overlay, then converts the transparent surface into the current read-only, movable, aspect-ratio-resizable pinned panel with no toolbar. That explicit Pin advances the surface to persistent copy behavior; context-menu Copy Screenshot is also always non-dismissing. Cursor rectangles are the sole hover authority: its body exposes open-hand feedback, its eight frame regions expose matching directional resize cursors, and one explicit app-controlled body-move interaction owns mouse-down, global-pointer-delta movement and mouse-up. That interaction sets the closed hand synchronously on mouse-down and retains it even when the pointer has not yet moved; it does not delegate body movement to the Window Server's drag-threshold lifecycle. No competing cursor stack or mouse-move setter participates. The pinned canvas context menu owns Copy Screenshot and Show/Hide Toolbar; toolbar visibility and annotation editability are one state transition, so hiding the toolbar always returns the image to read-only. Output failures stay visible and never silently advance the state machine.

Annotation document content and selection are published as one `AnnotationDocumentController.State`. Every add/delete/duplicate/undo/redo/rebase transaction reconciles selected IDs before the state is emitted, so SwiftUI cannot observe a selection that is absent from the matching document. The Canvas inspector receives one stable `AnnotationItem` value and edits a local identity-keyed draft; it never retains an array-lookup `Binding` across undo, deletion or view teardown.

Blur and Mosaic are modeled as fixed source-anchored effects: after creation they remain selectable but expose no selection handles or inspector scale controls, and pointer translation, keyboard nudging, alignment, distribution and resize geometry all exclude them so the effect cannot move away from or expand beyond the sampled pixels. Spotlight creation deliberately separates provisional and committed rendering: drag feedback is only an accent rectangle over the unchanged source canvas, while mouse-up commits the shared interactive/export vector renderer with a rectangular even-odd aperture over a translucent canvas-wide mask. The vector API takes explicit canvas bounds instead of only a zero-origin size; region live resize supplies its current viewport bounds every frame, including negative origins, so newly exposed desktop areas enter the mask synchronously while annotations retain their global anchors. Settings schema v9 stores the complete ordered, nonempty toolbar palette. Six Apple-system RGB colors are only factory defaults: any configured `#RRGGBB` color can be added or removed in Editor settings, deletion atomically redirects dependent defaults, and palette-only restoration either reinstates exactly the factory six or prepends the factory six while preserving custom colors and their tool defaults; neither mode mutates existing annotations or non-color settings. Changing color routes first to an active inline editor, then to the atomic selected-item transaction, and only otherwise changes transient tool style; beginning a new Text annotation reloads the Text default. Text styles persist an optional exact PostScript font name, where nil means the system font. Font-size and rectangle-radius defaults are stored as physical pixels and converted through each capture's backing scale. Legacy palette, tool defaults, font behavior and shortcut assignments are preserved during v1…v8 migration.

## Coordinates and Color

All selection geometry is represented in the global desktop coordinate space, including negative origins. Pixel conversion is performed only by `ScreenGeometry` with explicit display scale and top/bottom origin handling. Multi-display output maps AppKit frames into the default bottom-left Quartz bitmap context and draws each ScreenCaptureKit `CGImage` without a reflected CTM, preserving both display placement and each source's vertical pixel order. Captured `CGImage` values retain their source `CGColorSpace`; annotation colors are converted by system color management at render time, and Image I/O export embeds the selected profile when profile preservation is enabled.

## Data and Privacy

There is no Ushot-operated server, account, telemetry, analytics or system-profile collection. Captures, annotations, exports and history stay local; history is opt-in and stored under Application Support as inspectable PNG/JSON files. Settings and documents carry schema versions and explicit migrations.

Only an explicit manual update check reaches a GitHub Pages appcast. The 0.1.1 legacy request reaches a permanently absent endpoint; 0.1.2 and later use `/updates/v1/appcast.xml`. Its signed embedded restricted Markdown supplies release notes without a second network request or a link destination; after user acceptance, the client reaches the official GitHub Release asset. Normal HTTPS connection metadata is visible to contacted hosting providers, but no screenshot or user content is attached. The website-distributed public builds are not sandboxed, use deliberate ad-hoc signing, have no Developer ID/notarization and disable Hardened Runtime as described by the update trust boundary. Apple Developer Program membership is not required for this stage. Local development configurations may continue using Hardened Runtime and Apple Development signing.
