# Security Policy

## Supported versions

Security fixes are provided for the latest published Ushot release. Untagged builds and builds taken directly from `main` are development artifacts, not a supported distribution channel.

## Reporting a vulnerability

Please do not disclose an unresolved vulnerability, signing-key concern or exploit in a public issue.

Use **Security → Report a vulnerability** in the [Ushot repository](https://github.com/isCheneycc/ushot) when GitHub Private Vulnerability Reporting is available. If that control is unavailable, contact the repository owner through the GitHub profile and ask for a private reporting channel without including exploit details in public.

Include the affected version, macOS version, reproduction conditions, impact and the smallest safe proof of concept. Do not include real screenshots, clipboard contents, credentials or other people's data.

## Release and update trust

- Only assets attached to the official [`isCheneycc/ushot` releases](https://github.com/isCheneycc/ushot/releases) are Ushot releases.
- Ushot is not currently distributed with a Developer ID signature or Apple notarization. Initial installation therefore requires an explicit Gatekeeper quarantine-removal step documented in `README.md`.
- The complete appcast, including each embedded restricted-Markdown release description, must pass Sparkle `SURequireSignedFeed` validation before any item is accepted. From 0.1.3 onward the host sets `SUMaximumSignedAppcastContentLength=1048576`; the downloader rejects a declared `Content-Length` above the 1 MiB authenticated-prefix plus fixed 512-byte trailer bound before accepting the body and enforces the same 1,049,088-byte ceiling incrementally for chunked or otherwise undeclared responses. The framework must expose `SUFeedDownloadSizeLimitVersion=1`. This temporary-feed limit never applies to the persistent ZIP/archive download. Parsed `SUAppcastItem` values can collapse duplicate or namespace-confused metadata, so the fork additionally delivers the exact authenticated XML bytes to Ushot after EdDSA verification and before parsing. The host sets `SURequireHostSignedAppcastValidation=true`, requires framework marker `SUHostSignedAppcastValidationVersion=1`, and rejects duplicate, misplaced, wrong-namespace, DTD/entity or otherwise noncanonical input before parsed-item policy runs. A missing/rejected hook fails closed as an appcast parse error. The client still requires `signingValidationStatus == .succeeded` and keeps `shouldDownloadReleaseNotes` false. Detached release-note URLs, item links, full-release-note URLs and delta enclosures are rejected rather than fetched or rewritten; publishing also rejects links, images, raw HTML, autolinks, entities and URL/domain/network-address-like text in every retained description.
- The legacy `updates/appcast.xml` path used by 0.1.1 remains permanently absent. GitHub Pages may publish only the signed `updates/v1/appcast.xml` path used by the 0.1.2 hardened transition and later; release notes are not a separately hosted trust object.
- The published 0.1.2 runtime pins the reviewed `isCheneycc/Sparkle` fork at immutable tag `2.9.5-ushot.2` and revision `f4d8362bf9b6231596db3a0cc8812fdca8100961`. It sets `SURequireExactUpdateVersionIdentity=true` and `SURequireEdDSAUpdateArchiveSignature=true` and accepts its embedded framework only when `SUUpdateVersionIdentityHardeningVersion=1`, but predates the authenticated raw-XML hook. Published fork tag `2.9.5-ushot.3` is the historical authenticated-XML-hook predecessor and was never embedded in a published Ushot build. The published Ushot 0.1.3 manual transition pins fork tag [`2.9.5-ushot.4`](https://github.com/isCheneycc/Sparkle/releases/tag/2.9.5-ushot.4) at revision `3d81360ff115ffb80222c2723d72cb4cfa802774` (SwiftPM ZIP SHA-256 `d8d36e5b5ee9e97b17babc1beeb26795b96558cafe5450130aafa5b169d5c829`), retains those checks and adds the host hook, bounded-feed key and two later framework markers above. Before installation, the fork must compare the extracted app's `CFBundleShortVersionString` and `CFBundleVersion` exactly with the signed appcast identity and reject a missing or failed archive EdDSA signature without falling back to matching application code signing. A valid HTTPS download alone is not sufficient. The fork's publication was only dependency evidence; Ushot's separate protected Release establishes direct-download availability but does not validate an in-app update.
- The runtime fork does not replace the official upstream Sparkle 2.9.5 publishing tools. The protected workflow downloads the checksum-pinned official archive afresh and extracts it into a new directory for each feed-signing run; it never trusts a writable tools cache.
- The protected release pipeline independently extracts the final ZIP, binds both enclosed bundle versions to the signed appcast, and applies the same fail-closed raw XML structure rules before signing or extending a feed. Existing network feed bytes remain bounded and opaque until EdDSA verification succeeds. Credential-free release/input builders and a separate fixed-source signing-validator builder are isolated from a secret-free `release` approval and the job-level feed-only `update-feed-signing` runner; that runner never compiles repository code. The builder produces an ad-hoc-signed authenticated-XML validator and Ed25519 public-key deriver in one exact two-file artifact. Every Artifact recovery is selected by immutable ID and uses the pinned official downloader in fail-on-digest-mismatch mode. The signer rebinds both binaries by REST identity, independent SHA-256 values, exact layout and code signatures, uses only the prebuilt deriver for private/public-key identity, and uses the XML validator after feed authentication but before any XML normalization. It then immediately preserves the accepted feed by immutable artifact ID before a separate no-key job re-downloads and rebinds that same helper artifact for mutable repository validation of a disposable copy; validation has no implicit Swift/SwiftPM build fallback. A clean no-checkout job packages those same digest/size-bound bytes for Pages. GitHub Release publication and read-only deployment admission have no signing key, and the final Pages/OIDC runner executes only the pinned deploy action without checking out repository code. Those publication gates and the hardened runtime are complementary, and neither is operational evidence by itself. Protected workflow run [`31078896953`](https://github.com/isCheneycc/ushot/actions/runs/31078896953) published Ushot 0.1.3 (build 4) on 2026-08-06 with `publish_update_feed=false` and anonymously verified exactly five assets while both appcast URLs remained HTTP 404. The complete 0.1.3 → 0.1.4 clean-account, authenticated-XML, tamper, exact-version-mismatch and recovered-key matrix then passed before protected run [`31141110871`](https://github.com/isCheneycc/ushot/actions/runs/31141110871) published 0.1.4 (build 5) as the first production feed item. Protected run [`31864175412`](https://github.com/isCheneycc/ushot/actions/runs/31864175412) published Ushot 0.1.6 (build 7), anonymously verified its five immutable assets and extended the authenticated feed after revalidating every retained item.
- Developer ID and notarization remain disabled while the hardened ad-hoc update path is validated. Apple Developer Program membership is not required for this stage, and notarization is not a substitute for Ushot's update signature policy.
- A release may extend an authenticated appcast only when both its stable semantic version and positive decimal build number are strictly greater than every retained item. Appcast RSS/Sparkle namespaces, direct element hierarchy, uniqueness and prohibition of DTD/entity input are validated against raw XML before signing and again by a 0.1.3-or-later client after signature authentication.
- The production EdDSA private key, Apple signing credentials and notarization credentials must never be committed, printed in CI logs or attached to a release. The general `release` approval environment contains no key; the update key may exist only as `SPARKLE_ED25519_PRIVATE_KEY` in the protected `update-feed-signing` environment. Before it derives or signs anything, the protected signing step verifies fixed reviewed SHA-256 values for every repository shell script allowed to see the in-memory key, strict code signatures for freshly extracted checksum-pinned official Sparkle tools, and the separately built precompiled public-key deriver's artifact identity, SHA-256 and code signature. The signing runner must not invoke a source interpreter or compiler. Any local Keychain copy is rotation staging only; the steady state is the feed-only protected secret plus an independently recovery-checked encrypted backup set outside the workstation. The public EdDSA key is embedded in the application.
- The pre-0.1.3 key rotation uses public key `+zRL11/2yYePt5O+OetThnLGwyvAvFtPPXxiBBOTTjE=` and does not rewrite the historical key embedded in published 0.1.1/0.1.2 artifacts. The owner explicitly declined iCloud and accepted a single-provider exception: only client-side-encrypted ciphertext may be committed to the dedicated private `isCheneycc/ushot-signing-key-backup` repository, while its new high-entropy password remains outside GitHub. This is off-device disaster-recovery storage, never a plaintext-secret source or CI input, but it is not an independent provider because the same GitHub account controls the signing Secret. Account loss, repository deletion or lockout can therefore strand the update chain.
- The accepted ciphertext is fixed at private archived root commit `9fe3d07a31bad91c6b75142955f31d1c30816ec1`, SHA-256 `f308c694d6597a52a700ab4f9b97386ee17bd5332ad7725655fd13ab666155d0`. A fresh clone passed Git-object, exact-file, header and digest validation against the locally recovery-checked bytes before the protected signing Secret was replaced through a non-logging stdin path.
- A suspected private-key disclosure stops publication immediately. Preserve evidence, rotate credentials through a verified migration path, and do not publish a replacement feed until already-installed clients can authenticate it.

## Privacy-sensitive diagnostics

Security reports and application diagnostics may contain versions, lifecycle states and error categories. They must never contain captured pixels, annotation text, clipboard values, filenames, file contents, update keys or a system profile.
