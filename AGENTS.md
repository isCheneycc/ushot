# AGENTS.md

## Engineering rules

- Do not run a full type-check or full build after every small edit. Use broader validation only for broad changes; otherwise call out what still needs attention.
- Fail fast. Do not swallow errors or hide failures behind fallback behavior.
- Fix root causes instead of layering symptom-specific patches.
- Keep critical paths observable with privacy-safe logs and explicit lifecycle reasons.
- Preserve traceability at every important workflow boundary.
- Update this file and the product documentation when the technical stack or product direction changes.
- Ask before creating a branch for a large refactor or experimental change.
- After every completed change that affects app code or resources, build the stable locally signed Release app, replace `/Applications/Ushot.app`, relaunch it, and verify that the installed binary matches the new artifact before handing the task back. Do not leave the user running an older installed app after reporting completion. This local development install is distinct from the intentional ad-hoc public artifact.

## Update and distribution product contract

- Direct-download GitHub Releases and the production Sparkle updater are independent readiness gates. The protected workflow defaults to `publish_update_feed=false`: it must still build, validate, publish and anonymously download-verify exactly the five versioned Release assets, while skipping Sparkle-tool/current-feed access, private-key signing, Pages artifact creation and appcast deployment. Only an explicitly reviewed `publish_update_feed=true` run may extend and deploy the production feed. A direct-download Release must never be described as proof that self-update is ready.
- Release capabilities must remain split across fresh runners: read-only admission, credential-free release-artifact building, bounded opaque signing-input preparation, a separate credential-free signing-validator build, a secret-free `release` approval, a job-level feed-only `update-feed-signing` runner, immediate immutable preservation of the authenticated feed, credential-free runtime validation of a disposable copy, clean no-checkout Pages packaging, secret-free GitHub Release publication, read-only deployment admission and a final deploy runner that executes only the pinned Pages action. Every artifact handoff uses the producer's immutable artifact ID and a download implementation configured to fail on digest mismatch, plus independently bound name/content digest/size where applicable. The signing runner must never compile or build repository code: it may execute only pinned actions, fixed reviewed shell, checksum-pinned official tools and the exact prebuilt authenticated-feed validator plus public-key deriver recovered together by artifact ID, REST digest and independent binary SHA-256 values. No mutable repository runtime may execute there after signing and before the feed is preserved, and the final runner with Pages/OIDC write authority must never checkout or execute repository code. The no-feed path still requires `release` approval but must not build or download the signing validators, download signing inputs, start the signing environment, read the private key or create a Pages payload.
- Ushot 0.1.1 is the first direct-download preview and remains pinned to the legacy `/updates/appcast.xml` endpoint, which must stay permanently absent. Ushot 0.1.2 (build 3) is the published first manually installed hardened transition: its immutable five-asset GitHub Release shipped with `publish_update_feed=false`, and the new `/updates/v1/appcast.xml` endpoint remains absent. Because parsed `SUAppcastItem` values cannot prove that authenticated XML contained no duplicate or wrong-namespace metadata, Ushot 0.1.3 (build 4) is a second manual GitHub-only transition that must also ship with `publish_update_feed=false`; it is not yet published. The first permitted v1 feed item and online update is 0.1.4 (build 5), and the feed must not be deployed until the recorded 0.1.3 → 0.1.4 clean-account, raw-XML, tamper, version-mismatch and recovered-key matrix passes.
- The protected `release`, feed-only `update-feed-signing` and `github-pages` environments must allow only the exact currently approved release tag rather than a wildcard whenever they participate. `release` contains no update key; `SPARKLE_ED25519_PRIVATE_KEY` may exist only in `update-feed-signing`. Failed or superseded tags remain permanently absent from every applicable allowlist and must never receive environment approval, because immutable workflow source attached to an old tag cannot be revoked by changing `main`.
- Update access is user-initiated only. Ushot must not check at launch or on a schedule, download automatically, or send a system profile. The sole normal network entry is **Check for Updates…**, located after Settings and before About Ushot in the menu-bar menu.
- The fixed HTTPS appcast for the hardened chain is `https://ischeneycc.github.io/ushot/updates/v1/appcast.xml`; the updater delegate must override UserDefaults/argument feed changes with that value. The legacy `https://ischeneycc.github.io/ushot/updates/appcast.xml` endpoint must remain HTTP 404 permanently so a 0.1.1 client can never enter a runtime path that lacks Ushot's exact-version and strict-archive-signature hardening. Release notes are Markdown embedded directly in the signed appcast and must never cause a detached-notes request. Update archives may come only from `https://github.com/isCheneycc/ushot/releases/download/...`; GitHub-controlled asset redirects are part of the archive transport boundary. No screenshot or user content may enter a request.
- `SURequireSignedFeed` verification is mandatory for the complete appcast, including every embedded description, and signed-feed failure recovery must remain permanently disabled with `SUSignedFeedFailureExpirationInterval = 0`. From 0.1.3 onward the host must set the positive integer `SUMaximumSignedAppcastContentLength=1048576`; Sparkle may receive only that 1 MiB authenticated prefix plus its fixed 512-byte signed-feed trailer. Appcast transport must reject an oversized declared `Content-Length` before accepting its body and enforce the same 1,049,088-byte wire ceiling incrementally for chunked or otherwise undeclared responses. The embedded framework must expose `SUFeedDownloadSizeLimitVersion=1`. This limit applies only to the temporary appcast download and authenticated XML prefix, never to the persistent ZIP/archive download. The fork must pass the exact authenticated XML bytes to the host after EdDSA verification and before XML parsing; the host must also set `SURequireHostSignedAppcastValidation=true`, implement the validation hook and require framework marker `SUHostSignedAppcastValidationVersion=1` before any request. Rejection or loss of the hook owner must fail as an appcast parse error. Parsed `SUAppcastItem` policy remains defense in depth and may accept an item only when its `signingValidationStatus` is `succeeded`. `shouldDownloadReleaseNotes` must always return false, and every update archive must independently pass Sparkle EdDSA verification. A missing/changed public key, invalid signature, raw-XML violation, oversized response, feed error, version mismatch or install failure must fail closed, remain visible and keep the existing app intact. HTTPS or a matching checksum never substitutes for EdDSA authenticity.
- Every non-seed appcast item must contain exactly one nonempty `description` with `sparkle:format="markdown"`. Item-level `releaseNotesLink`, `link`, `fullReleaseNotesLink` and delta enclosures are forbidden. Release-note source is restricted Markdown: links, images, raw HTML, autolinks, entities and URL/domain/network-address-like destinations are all forbidden. The pipeline and the 0.1.3-or-later authenticated-XML hook must both fail closed on duplicate or misplaced metadata, wrong namespaces, DTD/entity declarations and every other noncanonical structure before parsed item policy can collapse it.
- The appcast display/build versions, tag, enclosure filename and the enclosed app's `CFBundleShortVersionString`/`CFBundleVersion` are one identity. Both a new stable semantic version and its positive decimal build number must be strictly greater than every retained item in the authenticated production appcast, using comparison that cannot overflow on long decimal components. The protected release workflow must extract the final ZIP and reject any identity mismatch before signing or publishing. The published 0.1.2 runtime embeds the reviewed Ushot Sparkle fork from `https://github.com/isCheneycc/Sparkle` at exact immutable tag `2.9.5-ushot.2` (revision `f4d8362bf9b6231596db3a0cc8812fdca8100961`), sets `SURequireExactUpdateVersionIdentity=true` and `SURequireEdDSAUpdateArchiveSignature=true`, and requires framework marker `SUUpdateVersionIdentityHardeningVersion=1`; it does not contain the later authenticated-XML hook. Fork tag `2.9.5-ushot.3` is the published historical authenticated-XML-hook predecessor and was never embedded in a published Ushot build. The 0.1.3 transition must instead pin exact immutable fork tag `2.9.5-ushot.4` (revision `3d81360ff115ffb80222c2723d72cb4cfa802774`, SwiftPM ZIP SHA-256 `d8d36e5b5ee9e97b17babc1beeb26795b96558cafe5450130aafa5b169d5c829`), retain the existing gates and add the host signed-appcast validation, bounded-feed configuration and three framework markers above. The fork must reject a post-extraction short/build mismatch and a missing or failed archive EdDSA signature without accepting matching application code signing as a substitute. Official upstream Sparkle 2.9.5 publishing tools remain the appcast/signing implementation. These source requirements do not prove Ushot release readiness: the production feed remains blocked until the 0.1.3 artifact and complete 0.1.3 → 0.1.4 matrix have recorded evidence.
- Only one manual update transaction may exist at a time. Its admission, checking, download, verification, installation, cancellation and relaunch outcomes must have explicit owners. Capture/tools, history operations, Canvas editors and pinned editing/output share the update-admission boundary: active work rejects update admission, new work is rejected while an update owns the boundary, and relaunch is postponed until the same query reports no active work.
- The initial public GitHub artifact intentionally uses ad-hoc signing, no Team ID, no Developer ID, no notarization and no `get-task-allow`. Its public configuration disables Hardened Runtime because ad-hoc re-signing plus Library Validation can prevent Sparkle components from loading. Every app mode must embed Sparkle, link it through `@rpath/Sparkle.framework/Versions/B/Sparkle`, and carry `@executable_path/../Frameworks` in `LC_RPATH`; source, build, package and local-install gates must reject a missing runtime path. Local Apple Development-signed builds do not prove that public self-update works.
- Initial installation instructions may remove only `com.apple.quarantine` from `/Applications/Ushot.app`, and only after the user obtains the DMG from the official GitHub Release. Never recommend `xattr -cr`, a recursive command against a broad directory, or applying the workaround to third-party downloads.
- The non-Developer-ID path is not release-ready until the 0.1.3 → 0.1.4 clean-account test verifies authenticated raw-XML rejection, Sparkle helper loading, exact short/build mismatch rejection, independent EdDSA rejection of tampering, atomic replacement, relaunch, quarantine behavior and Screen Recording permission behavior. Documentation must state that Screen Recording permission may need to be granted again.
- Developer ID distribution remains disabled until the hardened runtime and its strict archive-EdDSA behavior pass the complete update-transition and tamper-rejection matrix. Notarization alone does not satisfy this requirement. Joining the paid Apple Developer Program is not required for the current ad-hoc GitHub Release and hardened-update rollout.

## Region capture product contract

- Region mode freezes every participating display before any selection overlay is presented. That frozen desktop is the visual and pixel source of truth until the user cancels or commits an output.
- While the initial region selection remains unlocked, its magnifier must follow the pointer synchronously and sample only that frozen desktop. The lens uses rounded pixel-content clipping, a subtle shadow and dual-contrast hairline keylines—never an opaque padded black frame. Its compact center marker identifies the actual sampled pixel even when the crop shifts at a display edge, and the magnifier disappears once confirmation locks the selection.
- Region capture is a selection-confirmation workflow, not a screenshot-preview workflow. Mouse-up retains the frozen desktop, selected pixels and outside mask, then shows exactly one blue selection border with eight working resize handles, a transparent annotation surface and the complete annotation/output toolbar with Pin and Cancel added. Every point on each blue border edge is a resize target with the matching directional cursor; users do not need to hit a visible handle. Pinned-image-only controls—Click Through, Temporarily Hide Image and Open Canvas Editor—must be absent until the region has actually transitioned through Pin. Confirmation must not expose a cropped screenshot or pinned-image window.
- Every confirmation-handle center must sit exactly on the blue selection border. Any enlarged hit-target margin belongs to transparent chrome outside the selected desktop frame and must never inset the visible handles or change the selected/output geometry.
- The transparent confirmation canvas must exactly match the selected desktop frame and must receive every interior pointer event; only the eight resize hit regions may route to the surrounding chrome. Once confirmation begins, every full-screen frozen-overlay window is visual-only and must ignore pointer events, leaving the annotation panel as the single input owner. Mixed flipped/non-flipped AppKit layout must never distort that frame or leave either overlay or chrome intercepting annotation input.
- Mouse-up and double-click must never materialize or pin an output implicitly. An internal frozen-pixel crop may be cached for effects and final composition, but it is not a completed screenshot and must not replace the frozen-overlay presentation.
- The confirmation toolbar keeps every annotation and capture-output tool functional while omitting controls that operate only on an existing pinned window. Successful Copy or Save resolves the latest composite, closes the complete overlay/annotation-surface/toolbar group and ends capture; cancelling a Save panel leaves confirmation active. Cancel and Copy/Save must leave any existing pinned image untouched.
- Pin resolves the latest composite, closes the capture overlay, and advances the confirmation surface into the pinned-image lifecycle. It may replace the previous current pinned image only after composition succeeds.
- Explicit Pin is not governed by the automatic-pinned-presentation preference.
- Confirmation presentation and frame updates must not animate. With Select active, dragging empty canvas space moves the complete selected desktop frame; existing annotations keep their canvas-local geometry and move with it. During a live resize, the transparent annotation canvas is instead a 1:1 viewport into the original global-desktop document: changing an edge may reveal or clip content, but must never translate or non-uniformly scale existing annotations, selection handles or stroke widths in intermediate frames. The canvas and chrome geometry must update synchronously before drawing. Mouse-up then recrops the original frozen desktop image off the main actor and rebases the document plus its undo/redo timeline to the committed selection without creating a second visual-only handle layer.
- The initial confirmed selection, every live resize frame and the mouse-up commit must use the same canonical whole-point desktop frame. Never preview fractional AppKit pointer geometry and only integralize at commit: changing the backing-pixel phase during a drag makes otherwise stationary annotations shimmer or snap on release.
- Capture admission is atomic. If any capture session—including an uncommitted region confirmation—is active, a repeated global capture shortcut must be rejected non-modally without resetting, cancelling or otherwise mutating the active session. It may provide a beep and privacy-safe log, but must never run a hidden modal alert behind capture-level panels or steal input from the existing toolbar and overlay.
- A region created through Pin preserves the selected desktop frame, remains movable and proportionally resizable, starts without the quick-annotation toolbar, and is read-only by default; ordinary pointer input must never keep editing annotations after Pin.
- A successful toolbar Copy or screenshot-level `Command-C` on a newly presented window/display capture writes the latest composite and then closes its image and toolbar. Native text-field copying remains native, output failure leaves the screenshot available for retry, and automatic copying never triggers this dismissal. A region advanced through explicit Pin remains persistent after toolbar/keyboard copy, as does Copy Screenshot from any pinned-image context menu. Copy and Save run as generation-qualified output transactions: they may start only from committed region geometry with one mutation owner, freeze canvas/resize/toolbar mutation until completion, and validate the same desktop frame before writing. Escape, Cancel, replacement and application termination invalidate the transaction so a stale renderer can never write output, release a newer transaction or fire a late lifecycle callback. Output failure must finish and unlock the matching transaction before presenting exactly one visible error above every capture-level surface; never run a hidden modal alert while screenshot input is frozen.
- A read-only pinned image uses an open-hand cursor over its movable body, switches to an uninterrupted closed hand immediately on mouse-down—even before any movement crosses the drag threshold—and shows the matching horizontal, vertical or diagonal frame-resize cursor over every resizable edge and corner. Cursor rectangles are the single hover owner; one app-controlled body-move interaction owns mouse-down, global-pointer-delta movement and mouse-up as a single lifecycle. Do not delegate pinned-body movement to Window Server dragging, which can replace the closed hand while the pointer is held below its movement threshold. The active press must not compete with cursor-stack pushes or mouse-move setters.
- A pinned image's context menu exposes Copy Screenshot and Show/Hide Toolbar. Showing the toolbar enables annotation editing and restores Click Through, Temporarily Hide Image and Open Canvas Editor; hiding it ends any active edit and restores read-only input.
- Mouse-up must return promptly: crop the frozen selection off the main actor, cache the frozen overlay image, and prepare/reuse the complete region toolbar instead of constructing it synchronously after selection.
- Smart region snapping is enabled by default. Hovering identifies the topmost frozen ScreenCaptureKit window immediately; clicking accepts it, while dragging still creates a manual rectangle. Only front-to-back, layer-zero windows owned by another application are valid candidates: menu-bar, Dock, desktop and WindowServer surfaces must be rejected both during discovery and hit testing so they can never hide cross-application windows. With optional Accessibility permission, the same hover path refines the candidate to useful controls inside the owning app. Window snapping must keep working when Accessibility is absent, denied or revoked, and Ushot's overlay must never be queried as the target element.
- Keep the selection overlay, transparent annotation surface, confirmation toolbar and pinned panel as distinct lifecycle owners, and log frozen-desktop readiness, region geometry, preparation timing, toolbar placement, Copy/Save/Pin intent, editing-state transition and close reason.

## Annotation editor state contract

- Crop is not a user-facing annotation tool: it must be absent from the region/pinned quick toolbar, the full Canvas Editor rail and shortcut settings, and no keyboard shortcut may activate it. Preserve decoding and authoritative rendering of legacy crop state so existing documents remain readable and exportable.
- Publish each annotation document and its valid selection as one atomic observable state. A render must never expose selected IDs that are absent from the document emitted in that same transaction.
- SwiftUI inspectors must edit a stable value draft keyed by the selected item's identity. Never create a long-lived `Binding` whose getter force-resolves an item ID from a mutable annotations array; undo, delete, replacement and view teardown must not crash while the inspector graph is being dismantled.
- A full Canvas Editor window is the exclusive mutation owner for its `AnnotationEditingSession`. Before it is shown, the matching pinned surface must commit or reject active inputs, end inline text, hide its quick toolbar and become a read-only mirror without clearing the shared selection or preview exclusions; that mirror must draw no annotation handles or text chrome. Editor close releases a generation-qualified lease only after window teardown, ignores stale releases after an immediate reopen or pinned replacement, and restores only the toolbar visibility that preceded the handoff.
- Mosaic and Blur are fixed source-anchored effects. They may be selected, but they expose no resize handles or scale controls and must never be moved or resized after creation by pointer drag, arrow-key nudge, alignment, distribution or inspector editing.
- Freehand is a path-only brush annotation. It may be selected and moved, but it exposes no frame-resize handles or scale controls; its captured pointer path and stroke width must not be rescaled by a generic bounding-box transform.
- Filled, double and tapered arrowheads use a concave paper-plane rear join that converges diagonally into the shaft; they must never fall back to a flat triangle base or expose a gap/round-cap bulge at the join. Live preview, committed canvas, hit testing, style thumbnails and export share the same presentation-space geometry. Any future visual renderer-semantic change must advance the cached-preview render revision independently of the editable document schema, invalidate only affected legacy previews, and stamp the new revision only after a successful authoritative render.
- Highlight stores an opaque semantic color in `strokeColor` for editor and toolbar synchronization, while its matching `fillColor` owns the fixed translucent presentation alpha. New highlights use the factory yellow semantic color while it remains configured, otherwise they use the configured general default; legacy-default highlights still normalize to their historical yellow. Never use a transparent stroke as a renderer sentinel. Recoloring must preserve the fill alpha, and legacy sentinel styles must be normalized observably before editor admission.
- Removing any configured palette color never mutates existing annotations. When one is selected later, the toolbar presents that historical color as a disabled temporary current-value entry without restoring it to the configured palette or letting it recolor other annotations; choosing a configured color removes the temporary entry. Only a selected existing annotation may expose an off-palette current color—tool defaults and new drafts must be reconciled to configured colors.
- The annotation toolbar color control is a native secondary menu, never an `NSColorPanel`. Its ordered, nonempty, versioned palette is the single source of truth. A fresh install starts with red/orange/yellow/green/blue/purple, but every color—including those six factory defaults—may be removed, re-added or replaced only under Settings → Editor, and the factory six can be restored explicitly. Selecting a color must let native menu tracking end before document/TextKit mutation begins, must reuse the palette's cached swatch, and must log menu-action, queue and application timing without logging screenshot or text content.
- The annotation toolbar's numeric line-width field owns its raw editing string independently from the committed numeric style. It must preserve valid intermediate input such as `1.` so users can type `1.5` in order; never attach a formatter that rewrites the field during editing. Apply only lexically valid finite values, enforce the supported precision/range explicitly, and format once on commit or rejection.
- A line-width edit captures one stable semantic target when field editing begins. If one or more editable stroked annotations are selected, the field remains enabled even under Select, every valid keystroke previews those exact items immediately and commit creates one undoable document transaction without changing the persisted tool default. With no editable selection, the edit changes the current tool's independently owned creation default, leaves existing annotations and the document undo stack untouched, persists only on commit, and the very next annotation uses it without requiring a tool switch. Selection presentation style and creation-default style must never share mutable ownership; every atomic Add/Paste/Undo/Redo/selection update must resynchronize the displayed target, while clearing a selection restores the current tool default. Hiding the toolbar, Pinning or recycling it must cancel and detach both the field and canvas sides of any active transaction before changing lifecycle owner. A unit change first commits or rejects and detaches the current raw input, then converts and persists the default unit atomically.
- Text, Rectangle and Circle each have an independent default color in Settings. Changing color while a text editor or annotation selection is active edits that object; beginning a new Text annotation resets to the configured Text default. Text also has a configurable default installed font, with the macOS system font represented explicitly by a nil font name.
- Text annotations have one dedicated chrome in both active input and ordinary selected states: one accent border, font-size resize handles at the top-left, bottom-left and bottom-right corners, and a top-right close button that discards a new draft or deletes existing text through one undoable transaction. Text must never fall back to the standard eight-handle frame transform. Inline input keeps the native editor active while resizing and has a clear background; neither the AppKit text view nor its framing layer may fill the selected pixels underneath. The document baseline anchor is the rendering source of truth, so TextKit fallback-font metric changes must be corrected in place and focus-change commit to Core Text must not move the glyph line. Legacy text with rotation or non-uniform scale must remain selected and fail inline-edit admission observably until the native editor can reproduce its complete presentation transform; never flatten or discard that transform to make editing appear to work.
- Spotlight is available in the quick toolbar and full editor. While the user is dragging out a new Spotlight region, keep the source canvas unchanged and show only the normal accent selection outline; apply the dark translucent outside mask after mouse-up. Once committed, one rectangular clear focus region keeps the source pixels unchanged while the rest of the canvas is dimmed, and interactive/exported committed rendering must share that implementation. During region-canvas resizing, the committed mask must use the current live viewport bounds on every frame so newly revealed areas dim immediately rather than waiting for mouse-up recropping.

## Editor settings product contract

- Settings → Editor uses progressive disclosure: the page shows toolbar colors, one three-tool Text/Rectangle/Circle master-detail editor and one compact live preview. Only the selected tool's relevant controls are visible; do not restore separate always-expanded color/font/drawing sections.
- Every color control that displays a current value must pair the swatch, localized semantic name and exact `#RRGGBB` value. Unselected toolbar swatches stay compact, while the selected color receives a clearly visible ring and combined value summary.
- The default page owns only quick selection and tool defaults. Managing the complete toolbar palette belongs in the separate Manage Palette sheet. Any configured color may be added or removed, the last remaining color cannot be removed, and deletion must ask for a valid surviving replacement and atomically redirect every default that used it; existing annotations never change. Palette-only restore offers two explicit outcomes without resetting non-color editor defaults: replace the palette with exactly the factory six and redirect removed defaults to red, or restore the factory six while preserving every custom color and its tool-default ownership.
- Every Text/Rectangle/Circle item in the tool-default master list is one full-row button; its complete visible row, including transparent trailing space, must switch the selected tool.
- Text font selection is searchable and previews the actual family. Text, Rectangle and Circle summaries update immediately. Font size, line width and rectangle radius each default to physical pixels and independently support `px`/`pt`; changing a unit atomically converts its stored value at the Settings window's current display scale so the compact preview does not jump, then persists the value and unit together. New annotations apply the selected unit against the target capture's backing scale. Rectangle radius defaults to 4 px.
- Restore Editor Defaults affects only `EditorSettings`; it must not reset capture, output, shortcut, history or other application preferences.

## Shortcut settings product contract

- A global shortcut may use F1–F20 without Command, Option, Control or Shift. Every ordinary key still requires at least one of those persisted modifiers so a global registration cannot silently capture normal typing; Fn/Globe only exposes a standard function-key event and is never stored as a shortcut modifier.
- Function-key identity and display names come from one canonical physical-key mapping shared by recording, settings presentation and persistence. Registration remains transactional: a macOS-reserved or conflicting function key must surface the existing registration error and leave the previous shortcut active.
